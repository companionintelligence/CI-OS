# One-click automatic install

> Status 2026-10-18: implemented on branch `liam/companion-os-single-click-install`; unit-tested (121 tests), its image assertions pass on a real Ubuntu 26.04.1 build,
> **not yet proven end to end on a real install** (see [Status](#status)). Private & Confidential, Lifescope Inc.

"Install Companion OS (automatic)" erases one internal disk and installs Companion OS with **one question**: a dialog that names the disk and what is on it.
Everything else the installer would ask is answered for the user.

It does not replace the installer. It writes an autoinstall file and drives Canonical's own installer (`ubuntu-desktop-bootstrap`, which runs the `subiquity` server) through
its autoinstall path. The normal installer is still the default boot entry and still one click away from the same dialog ("Use the normal installer"). This page is about the
Ubuntu edition; the CachyOS edition installs with Calamares and has no such helper.

Evidence tags: **[V]** verified (run, or read in the cited file or snap), **[I]** implemented, not proven end to end, **[N]** not implemented or not checked.

## What the user sees

| Where | Entry |
|---|---|
| Live session | The launcher "Install Companion OS (automatic)" first in the dock and in the app grid. The stock installer is in the dock too. A copy is also placed on `~/Desktop`, but Ubuntu 26.04's live layer disables the desktop-icons extension (`disabled-extensions=['ding@rastersoft.com']` in its `livecd-rootfs.gschema.override`), so that copy is not drawn. [V] the override, read in the image; [I] the dock pin on a booted live session |
| Boot menu (ISO) | `Install Companion OS (automatic)` as the second GRUB entry. It boots the normal live session and opens the dialog by itself |
| Companion Stick menu | Not wired yet: the Stick's GRUB config is generated by `ci-stick` (`stick/crates/ci-stick/templates/grub.cfg.in`). The launcher works on a Stick |

The dialog:

* names the disk: model, size, device node, and **everything found on it**: every partition (`Windows (NTFS)`, `Linux (ext4)`, `contents not recognised` ...), a filesystem or
  RAID/LUKS signature on the whole disk, and any non-partition children,
* lists the other disks that will be left alone,
* shows a one-time password for the user `companion` (random, 16 characters from an alphabet without look-alikes),
* has **Erase the disk and install**, **Cancel** and **Use the normal installer**. **Enter never confirms: the default is Cancel**, also for a disk with nothing on it.

With more than one internal disk the user first picks one from a list (the NVMe/SSD is preselected). Nothing is guessed.

After the click a progress window shows the installer's state, with the sign-in details in every status line. When the installation is finished the computer **turns off**
(`shutdown: poweroff`, so a stick left in the machine does not boot the live session again): remove the USB stick, then turn it on. The first sign-in forces a new password (`chage -d 0`).

What is answered automatically (`build_autoinstall` in the helper; `ci-os-auto-install --plan` prints the file with the hash masked):

| Key | Value |
|---|---|
| `locale`, `keyboard` | `en_US.UTF-8`, layout `us` |
| `timezone` | `geoip` (UTC when offline) |
| `identity` | realname `Companion`, hostname `companion-os`, username `companion`, the SHA-512 hash of the one-time password, and `groups: {append: [docker]}` when the image has the `docker` group |
| `storage` | `layout: {name: direct, match: {path: <the chosen device>}}`: erase the disk, match by device path |
| `refresh-installer`, `drivers`, `codecs` | all `false`: no installer self-update, no proprietary drivers or codecs |
| `updates` | `security` |
| `shutdown` | `poweroff` |
| `early-commands` | the target check (rule 5 below) |
| `late-commands` | `chage -d 0 companion`, and remove `/target/autoinstall.yaml` and `/target/var/log/installer/autoinstall-user-data` |

## Safety rules

These are the rules the tests pin. Each is a property of `ci-os-auto-install`, not of the user paying attention. The first version of this tool was reviewed independently on
2026-10-15; the review's findings are what most of rules 1-3, 6 and 8-9 are. The state sets of rule 6 were corrected on 2026-10-17 after the real enum of the 26.04.1 installer was read.

1. **Never the boot medium.** A disk is excluded when `/cdrom` is mounted from it (traced through partitions and `dm` parents), when `/cdrom` is a **loop device** and the disk
   holds its backing file (`losetup -nO BACK-FILE`, then `findmnt -T`; GRUB loopback, iso-scan, Ventoy), when any partition under it is mounted at or below `/cdrom`,
   `/isodevice`, `/rofs`, `/run/ci-os` or `/run/live`, or when it carries a Companion Stick label (`CI-EFI`, `CI-SHARED`, `CI-BOOT-A/B`, `CI-CACHE`, `CI-PERSIST`, `writable`,
   `casper-rw`) even if this session did not boot from it.
2. **Fail closed.** If `/cdrom`'s source cannot be traced to a disk or to RAM (a loop whose backing file cannot be resolved, an unexpected layout) the tool offers *no* disk and
   sends the user to the normal installer. It never guesses.
3. **Internal disks only.** Not removable, not hotplug, not `tran=usb`, not on a USB or Thunderbolt path in sysfs (this catches bridges that lie to `lsblk`), not an SD/eMMC card
   (`mmcblk*`), not read-only, not a loop/zram/ram/dm device, at least 25 GB. With several candidates the user chooses, so an external NVMe can never become the silent default.
4. **One consent, naming the target.** Nothing is written before the click, and the click is not the default key. A boot-menu entry only opens the dialog, so a Stick booted by
   accident in the automatic entry erases nothing. The helper strips `ZENITY_*` / `DIALOG_*` from the environment so exit codes cannot be remapped, and a zenity that fails counts as Cancel.
5. **The target is pinned three times.** After the click the disk list is classified again and must still contain the same disk with the same size; again just before the install is
   confirmed; and the autoinstall file carries an `early-commands` check that runs before any disk is touched: the disk's size must still equal the size that was shown, and the disk
   must not carry `/cdrom`. (Subiquity skips `early-commands` on a second attempt within one boot, which is why the two earlier checks exist.)
6. **One instance, one installer.** A non-blocking `flock` refuses a second click or a click while the boot-menu dialog is open. The helper refuses to touch an installer that is
   busy (next section), and a `/autoinstall.yaml` that is not its own symlink is never overwritten and never removed.
7. **The password never leaves the box.** Only its SHA-512 hash goes into the autoinstall file, which lives on tmpfs (`/run/ci-os-auto-install/`, mode 0600; `/autoinstall.yaml` is a
   symlink to it, so a crash leaves a dangling link that subiquity ignores) and is removed on success and on failure. The helper never prints the password (a test parses the script
   for it). It does appear in the argv of the zenity dialogs of the live session, which is a single-user machine and the password is one-time (`chage -d 0`).
8. **Failures are visible and honest.** Every API call checks the HTTP status; a refused confirmation is a failure, not a four-hour wait. Any exception shows a dialog. After a
   failure the autoinstall file is removed and the installer server is restarted **only if it is not installing** (`restart_if_idle`), so the next start is a clean one and a
   give-up after the four-hour wait cannot kill curtin in the middle of a write. The message says "Nothing was erased" only when the install was never confirmed, otherwise "The disk may
   be partly or completely erased".
9. **No disk tools of its own.** The helper has no `mkfs`, `wipefs`, `sgdisk`, `parted` or `dd`, and no `shell=True` (tested on the script text, and re-checked on the copy inside the
   ISO by `verify-iso.sh`). Dynamic text in dialogs is escaped (`&`, `<`, backslash), because a partition label is attacker-controlled input.

## The installer's states

The helper talks to the installer's server over `/run/subiquity/socket` (`GET /meta/status`, `POST /meta/confirm` with the JSON string `"/dev/tty1"`). The states are the
`ApplicationState` enum of the 26.04.1 snap (`ubuntu-desktop-bootstrap` rev 665, `subiquity/common/types/__init__.py`): `STARTING_UP`, `CLOUD_INIT_WAIT`, `EARLY_COMMANDS`,
`NEEDS_CONFIRMATION`, `WAITING`, `RUNNING`, `UU_RUNNING`, `LATE_COMMANDS`, `DONE`, `ERROR`, `EXITED`. [V] read in the snap; the helper's sets are `STARTUP_STATES`, `BUSY_STATES`,
`IDLE_STATES` and `AMBIGUOUS_STATE` at the top of `ci-os-auto-install` (lines 72-91).

One run goes through them in this order (`server/controllers/install.py`, lines 608-624): `STARTING_UP`, `CLOUD_INIT_WAIT`, `EARLY_COMMANDS`, `WAITING`, `NEEDS_CONFIRMATION`
(skipped if the kernel command line carries the bare word `autoinstall`, which this tool never sets), `RUNNING` (the install, curtin), `WAITING` again (the server waits for the
post-install settings), `RUNNING` (with `UU_RUNNING` for unattended-upgrades in the new system), `LATE_COMMANDS`, `DONE`.

| State | Meaning | The helper treats it as |
|---|---|---|
| `STARTING_UP`, `CLOUD_INIT_WAIT`, `EARLY_COMMANDS` | the server is starting and does not answer requests yet | waited out (`wait_ready`); for `is_busy` an unknown or start-up state counts as busy |
| `WAITING` | idle before the install **and again after curtin has written the system**; the name alone does not say which | **busy only if `/target` (or anything below it) is a mount in `/proc/self/mountinfo`, or a `curtin` process exists**; otherwise idle |
| `NEEDS_CONFIRMATION` | everything is answered; the server waits for `POST /meta/confirm` | idle (nothing is written) |
| `RUNNING`, `UU_RUNNING`, `LATE_COMMANDS`, `DONE` | the install is under way or finished | **busy**: never touch the server, never write a new autoinstall file |
| `ERROR`, `EXITED` | failed, or the server is exiting | idle |
| anything else, an unreadable mount table, a `pgrep` that cannot run | | **busy** (fail closed: a wrong "busy" costs one more click, a wrong "idle" restarts the server in the middle of writing a disk) |

The waits name every state that can follow: after the restart the helper waits for `NEEDS_CONFIRMATION`, the busy states or a failure (600 s); after the confirmation it waits for the
busy states or a failure (180 s); then it polls until `DONE` (at most four hours).

An earlier revision of the helper listed `POST_WAIT`, `POST_RUNNING` and `UU_CANCELLING`, which do not exist, and left `WAITING` and `LATE_COMMANDS` out, so a second click in the
post-install window passed the "already installing" guard. `StateGuardTests` (10 tests) pins the sets against the real enum, checks that every state is accounted for exactly once and
that each of the listed behaviours holds whatever the mount table says. A failed attempt can leave `/target` mounted; the next click then says "An installation is already running, or an earlier one left the new system mounted at /target"
and asks for a restart from the USB stick. That is safe and slightly annoying.

## How it works

```
click  ->  ci-os-auto-install
              flock; lsblk -J / findmnt /cdrom (/ losetup)  ->  classify disks, refuse if the medium is unknown
              (several candidates -> chooser)  ->  zenity confirmation: Cancel | Use the normal installer | Erase and install
              re-classify; wait for the server to finish starting, then refuse if it is busy (see the states above)
              write /run/ci-os-auto-install/autoinstall.yaml (0600), ln -s /autoinstall.yaml
              pkill the stock installer window; systemctl restart snap.ubuntu-desktop-bootstrap.subiquity-server.service
              poll  GET /meta/status  over /run/subiquity/socket   (sudo -n curl --unix-socket)
                NEEDS_CONFIRMATION -> re-classify once more -> POST /meta/confirm (HTTP 200 required)
                RUNNING / WAITING / UU_RUNNING / LATE_COMMANDS ... DONE   (the machine powers off by itself)
              on any failure: remove the file, restart the server only if it is idle, say honestly what happened
```

Files (all under `backends/ubuntu/chroot/payload/live-start/`, installed by `customize-chroot.sh` Step 10f, line 1042):

| Image path | Purpose |
|---|---|
| `/usr/libexec/ci-os/ci-os-auto-install` | the helper (python3 + zenity + curl + openssl + python3-yaml). On the stock 26.04.1 image `curl` is **not** installed; Steps 10b and 10d of `customize-chroot.sh` install it and Step 10f stops the build if any tool is missing. `sudo` is sudo-rs: `sudo -n` works as the helper uses it |
| `/usr/share/ci-os/live/ci-os-auto-install.desktop` | the launcher; `--live-setup` copies it to `~/Desktop` and `~/.local/share/applications` and marks it trusted |
| `/etc/xdg/autostart/ci-os-live-setup.desktop` | runs `ci-os-auto-install --live-setup`; does nothing outside a live session, so an installed system is untouched. In a live session it also pins the launcher first in the dock (`gsettings org.gnome.shell favorite-apps`, best effort: a failure is only logged) |

GRUB: `build-iso.sh` `add_auto_install_menuentry` (line 868, called by `generate_iso`) inserts one entry after "Try or Install Companion OS" that is a copy of it with `ci.autoinstall=1` on the
kernel line. Every existing entry and kernel line is unchanged; the build fails if the stock entry is not the expected shape. `--live-setup` sees `ci.autoinstall=1` in `/proc/cmdline` and opens the
dialog. The bare word `autoinstall` (which would make subiquity install unattended with no question) is never put on any line; `verify-iso.sh` asserts that. The stock 26.04.1 `grub.cfg` has the
entries "Try or Install", "safe graphics", "Boot from next volume" and "UEFI Firmware Settings", and the insertion was run on the real file: exactly one new entry, `loadfont unicode` and the menu colours present. [V]

What the installed machine gets from this path, and why each is there:

| Item | Mechanism | Tag |

## Interfaces for tests and debugging

```bash
ci-os-auto-install --disks   # candidate/excluded table, and whether the boot medium was identified
ci-os-auto-install --plan    # the chosen disk, the autoinstall file (hash masked); changes nothing; exit 3 when no safe disk
```

`CI_OS_AI_LSBLK_JSON`, `CI_OS_AI_CDROM_SOURCE`, `CI_OS_AI_LOOP_BACKING` (`<device> <fstype>`) and `CI_OS_AI_CMDLINE` replace the system's answers with fixtures (tests only).

Exit codes: 0 ok, 2 usage, 3 no safe target / medium unknown, 4 not a live session, 5 installer not ready or busy, 6 cancelled (or another instance is open), 7 install failed.

## Known limits

* It installs to **one** disk, wiping it. There is no dual-boot, encryption or manual partitioning in this path; the normal installer has them.
* Time zone needs a network for geoip; offline it is UTC.
* The Companion Stick's own boot menu has no automatic entry yet.
* The stock installer window (when the normal path is used) still shows Ubuntu's help slides and the Ubuntu roundel; the automatic path never shows them because its own progress window replaces the installer client.
* The helper is part of the installed system too (inert there). Whether it should be, is the open decision in [ubuntu-iso-layers.md](ubuntu-iso-layers.md), section 8.
* What changed on the way to 26.04.1 is in [ubuntu-2604-port-notes.md](ubuntu-2604-port-notes.md).
